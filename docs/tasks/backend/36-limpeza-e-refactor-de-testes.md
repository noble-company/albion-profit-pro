# 36 — Limpeza estrutural e refactor da suíte de testes

> Corrige **P1**, **P2**, **P4**, **P5** e **P6** de
> [../../04-revisao-fase-1.md](../../04-revisao-fase-1.md).

## Objetivo
Tirar o código morto, alinhar os domínios ao layout que o projeto escolheu, e reescrever a
suíte em cima de fixtures compartilhadas e de **payloads reais** em vez de dicts inventados.

## Por que

### Código morto e layout desalinhado (P1, P2)
- `src/exceptions.py` — **vazio**, nunca importado por ninguém.
- `src/recipes/router.py` — **vazio** e não registrado em `src/main.py`.
- `recipes/` não tem `schemas.py` nem `service.py`; a lógica mora em `scripts/`. Os outros cinco
  domínios seguem o padrão `router/schemas/models/service`.
- `ingest` põe a montagem de linha e o acesso ao banco dentro de `tasks.py`, enquanto `prices` e
  `api_tokens` têm `service.py`.

Arquivo vazio é pior que arquivo ausente: quem chega assume que existe algo ali e vai procurar.

### A suíte não isola nada (P4, P5)
- `_unique_email()` copiado em **5** arquivos, `_create_test_user` em **3**, helper de
  register+login duplicado.
- Praticamente todo teste tem `try/finally` com `DELETE` manual. Se o teste falha no meio, a
  limpeza pode ficar parcial e contaminar os próximos.
- O isolamento é feito com **IDs aleatórios num banco compartilhado** — funciona, mas esconde
  problemas de ordenação e deixa lixo acumulado.
- A fixture `db_session` (`tests/conftest.py:89`) é declarada e **nunca usada**.

### Os testes validam um contrato imaginário
Todo payload de teste foi escrito à mão. Foi exatamente por isso que os achados **N1** (prata
×10.000), **N2** (timescale não é identidade) e **N3** (`LocationId` não numérico) passaram
pelos 51 testes verdes — o dict inventado tinha `unit_price_silver: 100` e
`location_id: "1002"`, que *parecem* certos. Agora temos payload real versionado em
`backend/tests/fixtures/wire/`.

### Lixo de autogenerate (P6)
Cinco migrations carregam `# ### commands auto generated by Alembic - please adjust! ###` e
`import fastapi_users_db_sqlalchemy` não usado — silenciado por um per-file-ignore do ruff em
vez de limpo.

## O que implementar

### 1. Remoções e realinhamento
- Apagar `src/exceptions.py` (ou preenchê-lo com as exceções de domínio, se a task 24 criar
  alguma — decidir na hora, não deixar vazio).
- Apagar `src/recipes/router.py` ou implementá-lo e registrar. Se receita não tem endpoint
  ainda, apagar é o certo.
- Mover o acesso a banco de `src/ingest/tasks.py` pra `src/ingest/service.py`; a task fica só
  com orquestração (loop, retry, log).

### 2. Fixtures compartilhadas em `tests/conftest.py`
```python
@pytest_asyncio.fixture
async def usuario(db_session) -> User: ...

@pytest_asyncio.fixture
async def cliente_autenticado(client, usuario): ...      # devolve AsyncClient com header JWT

@pytest_asyncio.fixture
async def token_api(db_session, usuario) -> str: ...      # token cru pro ingest

@pytest.fixture
def payload_ordens_real() -> dict: ...                    # le tests/fixtures/wire/*.json

@pytest.fixture
def payload_historico_real() -> dict: ...
```
E usar a `db_session` que já existe, em vez de cada teste abrir seu próprio
`async_session_maker()`.

### 3. Limpeza automática, não manual
Uma fixture `autouse` que, ao fim de cada teste, apaga as linhas criadas — ou, melhor, uma
fixture que roda o teste **dentro de uma transação com rollback no final**. A transação é o
padrão certo, mas exige atenção porque o código sob teste dá `commit()`: o jeito usual é abrir
uma conexão externa, iniciar uma transação aninhada (`begin_nested`) e fazer o sessionmaker do
teste apontar pra ela. **Avaliar na implementação**; se ficar frágil com o Celery/asyncpg, a
fixture de limpeza por tabela resolve 90% com muito menos mágica.

### 4. Testes de contrato com payload real
Substituir os dicts inventados de `tests/ingest/` pelas fixtures reais, e adicionar:
- validação dos schemas contra os arquivos de `tests/fixtures/wire/` (já feita à mão nesta
  revisão, precisa virar teste);
- as premissas medidas como asserção explícita: prata múltipla de 10000, `Timescale` presente
  em {0,1,2}, `Expires` parseável. Se um patch do jogo mudar isso, o teste avisa.

### 5. Script de captura no repo
Trazer pro repo o sink usado nesta revisão, como `backend/scripts/capture_sink.py` (hoje ele
vive só no diretório temporário da sessão). É a ferramenta que permite repetir a captura a cada
patch do jogo — ver [../../03-contrato-ingest-real.md](../../03-contrato-ingest-real.md) seção 9.

### 6. Migrations limpas
Remover os marcadores de autogenerate e os imports não usados; tirar o per-file-ignore
`"alembic/versions/*.py" = ["F401", "I001"]` do `pyproject.toml` depois. **Não** reescrever o
histórico de revisões — só limpar o conteúdo dos arquivos.

## Depende de
Idealmente **por último** (depois das tasks 23-35), porque a suíte vai ser reescrita em cima do
schema novo. As fixtures de payload real (item 4), porém, podem — e devem — ser criadas **antes**
das tasks 25-29, pra servirem de teste de aceitação delas.

## Testes manuais
1. `uv run ruff check .` limpo, inclusive sem o per-file-ignore das migrations.
2. `uv run pytest tests/ -v` verde.
3. Rodar a suíte 2× seguidas sem recriar os containers → mesma contagem, sem falha por resíduo.
4. `uv run pytest tests/ -p no:randomly` e em ordem aleatória → mesmo resultado.

## Testes automatizados
A própria suíte é o entregável. Critérios objetivos de "pronto":
- Nenhuma definição duplicada de `_unique_email`/`_create_test_user` (checável com `grep`).
- Nenhum `try/finally` com `DELETE` manual nos testes.
- `tests/fixtures/wire/` usado por pelo menos um teste de cada tópico de ingest.
- Cobertura do wrapper síncrono da task Celery (o buraco do **C1**, ver task 23).
